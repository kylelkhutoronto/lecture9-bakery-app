Start and stop

  1. Open this folder in File Explorer. Click its address bar, type powershell, and press Enter.
  2. Type python app.py and press Enter.
  3. Open http://127.0.0.1:8000 in your browser.

Keep the PowerShell window open while using the app. Press Ctrl+C there to stop it. Decisions save automatically in bakery.db. Repeat the steps to return later.

If python is not recognized, try py app.py. If port 8000 is already occupied, stop the other server using it before starting this one. Python must be available; no extra packages are needed.

This guide also opens directly by double-clicking README.html, or through the app's Help link.

Using the app

1. Check the displayed day and calendar

A fresh database starts on Monday, November 23, 2026, with 13 previously accepted orders and 25 supplied Instagram messages across Monday–Sunday. The saved classroom date controls arrivals and deadlines. Your computer clock does not advance the app.

The calendar shows the displayed Monday–Sunday week: committed baking hours, available capacity, free hours, order counts, helper bookings, and each committed customer order with its product and quantity. Request cards show the pickup day's booked/free hours beside the decision buttons. Pending requests reserve no hours. The top sales and helper-cost totals cover this same week, using pickup dates.

2. Review the inbox

Click Fetch messages to process messages received up to the displayed day. Future messages stay unavailable. Fetching again does not duplicate orders. Each fetched message is checked using fixed rules. Eligible new orders remain in the inbox for your decision. Use Accept order individually, or Reject request, optionally adding a reason. Requests that fail the rules when fetched are automatically rejected and appear in the visible Incompatible orders section for that received day, with a permanent record in Decision history.

Valid changes and cancellations apply automatically when their messages are fetched. A rejected change leaves the original order intact. Messages are processed by received date and message number; capacity is checked against work already accepted.

3. Book help when needed

Use + Helper on an eligible calendar day, or expand Book a helper for another date. A helper costs $100 and adds four hours for that day. Book at least two calendar days ahead. One helper is allowed per day; the app does not offer helper cancellation.

Book before clicking Fetch messages if that inbox may need extra capacity. Unlike the earlier build, advancing the date does not fetch messages automatically, giving you a chance to book help first. Requests rejected when fetched stay rejected after a helper is booked. Already-pending eligible requests are reassessed when you accept them.

4. Accept remaining requests and advance

Fetch all arrived messages first; the advance button is disabled while any remain unfetched. Reject any requests you do not want. Then press Accept all and go to next day. The app performs these steps in one transaction:

  1. Check remaining arrived requests one by one, in message order. Accept each that fits; reject any that no longer meet the rules. Accepting one can consume the space another needs.
  2. Close the displayed day at a simulated 5 PM and mark its accepted pickups as Picked up.
  3. Move the classroom date forward one day. Review capacity and book help if needed, then click Fetch messages for that day.

The button does not wait for real-world 5 PM. There is no undo-day button or manual pickup confirmation in this version. After Sunday, you can continue advancing, but there are no further supplied message files.

5. Record another request

Use Record a request to enter a new order, change or cancellation received on the displayed day. Cupcake quantities mean dozens; cake quantities mean individual cakes. Use positive whole numbers.

For changes and cancellations, enter the original customer name and pickup date. Matching ignores letter case and must find exactly one accepted order. Changes replace its product and quantity. To move a pickup date, cancel the original order and enter a new request; both actions need sufficient notice. For cancellations, product and quantity are not used to change the order, but leave valid values in those required form fields.

6. Find, review and export

The order book can be filtered by customer/order number, pickup date and status. It contains every fetched new order, with Requested, Accepted, Rejected, Cancelled or Picked up status. Changes and cancellations link to the original order. The value/time columns describe the order itself; only committed statuses contribute to the weekly totals. CSV sales and baking minutes are zero for requested, rejected and cancelled orders.

Decision history retains original message text, outcomes, reasons and source identifiers. Its activity log records actions, including the Incompatible-to-Rejected transition. Valid and rejected changes/cancellations received today are also visible in their own section on the main page. Export all orders (CSV) exports the entire order book regardless of filters. In the database and export, collected means Picked up. A legacy ready status may remain from the previous app.

Business rules and totals

Product unitPriceBaking time
One dozen cupcakes$4030 minutes
One cake$1202 hours
  • One product per order. All baking happens on the pickup date.
  • Base capacity is eight hours per day, rising to twelve with one helper.
  • New orders, changes, cancellations and helper bookings need at least two calendar days' notice. Monday for Wednesday qualifies; Monday for Tuesday does not.
  • Message notice uses its received date; helper notice uses the displayed booking date. Orders with pickup dates already past cannot be approved.
  • Changes recalculate capacity without counting the original order twice. Cancellations release its baking time and remove its sales from totals.
  • Only exactly one matching accepted order may be changed or cancelled. Previously picked-up, ready or cancelled orders do not qualify.
  • Picked-up orders still count as work performed on their pickup date. Cancelled orders count toward neither used hours nor sales.

Committed sales is the value of accepted and picked-up orders for the displayed week, excluding cancellations. It is not a payment record. Helper bookings is that week's booked helper cost. Sales less helpers subtracts helper costs only; ingredients and other costs are not recorded, so this is not profit.

Implementation details

app.py contains the local HTTP server, source parsers, database setup/migration, rule checks, actions and page rendering. It uses Python's standard library: http.server, sqlite3, csv, html.parser and date utilities. The interface uses server-rendered HTML, CSS and ordinary forms; JavaScript is not required.

Files and imports

bakery.db is the single persistent SQLite data file beside the app. A fresh database imports existing_orders.csv and InstagramOrders_Monday.html through InstagramOrders_Sunday.html once. Each message has a unique source identifier. Restarting preserves decisions; editing source files afterward does not reimport them.

When starting with the previous database, the app preserves existing records and moves helper bookings into days. It adds any missing Requested/Rejected order rows for previously fetched new messages, retaining order numbers already assigned, saved decisions, helper bookings and the classroom date. Unfetched messages wait for the Fetch button; restarting does not advance the date or reset choices. This is a revision of the same app and database, not a separate installation. The saved app.previous.py and README.previous.html are reference copies; do not run the previous code against the migrated database.

Data model

Table or viewPurpose
ordersOrder number, customer, product, quantity, pickup date, lifecycle status and source. Baking time required and order value are derived from product and quantity rather than stored again.
daysOne row per baking date, with the date a helper was booked, if any. Orders are associated with days by pickup date; triggers create missing day rows.
requestsOriginal message, source, received date, requested product/quantity/date, type, decision, reason and a foreign-key link to an order where applicable.
settingsSaved classroom date and initialization marker.
auditActivity records with the classroom date.
day_summary (view)Calculates capacity, order count, baking minutes and sales from days and orders. These totals are not stored as duplicate fields.

Hours are calculated in integer minutes, and prices use whole dollars. Each request is retained as an event; its raw text and parsed request fields represent what the customer asked at that time. Orders hold the current order facts. A change updates the existing order rather than creating another accepted order. There is one Orders row per new-order message, and changes/cancellations link to that same row.

States and actions

Fetching a valid new message creates an Orders row with requested status. An invalid one is created as incompatible and immediately transitions to rejected, recorded in the audit log. The linked message record is pending, approved or rejected. Accepting changes the same Orders row to accepted; rejecting changes it to rejected. An approved cancellation sets that order to cancelled. Closing the pickup day sets accepted orders to collected, displayed as Picked up.

assess() checks notice, target order and capacity. fetch_arrivals() checks newly arrived messages. decide_request() records approval/rejection and updates orders. act() handles form actions, and render() builds the page.

Actions use SQLite transactions with BEGIN IMMEDIATE and check rules before writing, including each bulk acceptance. Failed actions roll back. Successful forms redirect to the main page to avoid repeating an action on refresh.

Local serving and scope

The server binds to 127.0.0.1:8000 and serves the app, this guide and the CSV export. It does not serve arbitrary folder files. SQL values use parameters; displayed user text is escaped; cross-origin form submissions are rejected; exported customer names that resemble spreadsheet formulas are protected.

All automatic decisions are fixed rules. There is no AI, live Instagram connection, message sending, payment handling, customer ranking or automatic helper hiring. The Workflow Builder files are independent and are not used by the bakery app.

How this differs from the previous app

The layout and core baking constraints remain similar. The main change is how much of the order lifecycle the backend carries out automatically.

Both versions use the same prices, baking times, two-day notice rule, helper cost and capacity limits. Both provide manual request entry, order filters, history and CSV export. The current version follows the supplied classroom state/action framework more closely; the previous version gave the baker more individual confirmations.

Tests, backups and verification limits

From this folder, run:

python -m unittest -v test_bakery.py

The 15 automated tests passed after the app changes. They cover imports/restarts, notice and future-message checks, helpers and duplicate bookings, capacity, changes/cancellations, pickup transitions, escaped user text, sequential bulk acceptance, derived daily totals, the full supplied week with and without helpers, explicit/idempotent fetching, isolation of manual entries from unfetched imports, saved-choice migration, lifecycle rows, noncommitted export totals and HTTP form/export behavior.

Each test starts with a temporary SQLite backup of bakery.db and resets only that copy to the supplied source dataset. Tests do not change the real database and remain repeatable after you enter decisions. Database and source files must be present. The revised build was also checked in the in-app browser on a temporary database copy: desktop and phone widths, Monday acceptance/5 PM pickups, Tuesday fetching and the automatic Brown cancellation. No user orders were changed by those browser tests.

To back up: stop the app and copy bakery.db somewhere safe. To restore: stop the app and replace it with your backup. There is no in-app reset or undo. Keep app.py, this guide and the eight source files together.
